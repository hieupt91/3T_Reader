## MỨC NGHIÊM TRỌNG

### 1. Mở lại cùng một file PDF nhiều lần → tạo tab trùng lặp thay vì chuyển sang tab đã mở

**Cách tái hiện:**
1. Mở file `1 Dao giao sinh tu ky thu - in (1).pdf` (711MB/336 trang) từ dòng lệnh / file association.
2. Trong khi app đang chạy, mở lại **đúng file đó** thêm 3 lần nữa (double-click file trong Explorer, hoặc chạy `main.py <path>` lần nữa — cơ chế single-instance sẽ forward qua IPC).

**Kết quả thực tế:** Mỗi lần mở tạo **1 tab mới hoàn toàn trùng tên**, không kiểm tra file đã mở hay chưa. Đã xác nhận bằng ảnh chụp màn hình thật: 4 tab cùng tên `1 Dao giao sinh tu ky thu - in (1).pdf` xuất hiện liên tiếp. RAM tiến trình tăng dần theo từng lần mở: **419MB → 630MB → 762MB → 917MB** (đo trên tiến trình thật qua `tasklist`, khớp với mô tả ban đầu của người dùng 357MB→820MB). Sau khi đóng 3 tab thừa, RAM giảm về 453MB — cơ chế dọn tài nguyên khi đóng tab (`_dispose_tab_resources`) hoạt động đúng, chỉ riêng bước **mở lại** là thiếu kiểm tra trùng lặp.

**Kỳ vọng:** Mở lại file đã có tab mở phải **chuyển focus sang tab đó**, không tạo tab mới.

**File/hàm nghi vấn (đã xác định chính xác qua code + test headless):**
- `app/window.py:516` — hàm `open_document()`: luôn tạo `QWidget` + `PDFViewerWidget` mới và `self.tab_widget.addTab(...)` mà **không** duyệt `self._tabs_data` (dict lưu state từng tab, có sẵn `source_path`/`display_path`) để tìm tab đã mở file đó.
- `app/actions/file.py:100` — hàm `open_file()`: là điểm gọi chung cho cả menu "Tệp > Mở tệp", kéo-thả, và IPC single-instance (`window.open_external_files` → `_open_external_files_on_ui_thread` → `open_file`) — cũng không có bước kiểm tra trùng.

**Gợi ý hướng sửa (không tự thực hiện):** Thêm 1 bước kiểm tra ở đầu `open_document()` (điểm hội tụ duy nhất mọi luồng mở file đều đi qua) — so khớp `os.path.normcase(os.path.abspath(source_path))` với các tab đang mở trong `self._tabs_data`; nếu trùng thì `self.tab_widget.setCurrentIndex(...)` và return thay vì tạo tab mới.

### 2. Ứng dụng crash hoàn toàn (Windows fatal exception / access violation) khi thao tác với nhiều tab, trong đó có file rất nặng

**Cách tái hiện (ghi nhận được, không phải lúc nào cũng crash):** Mở file gốc 711MB ở tab 1, mở thêm 1 bản sao cùng nội dung ở tab 2 (RAM tiến trình ~680–900MB), chuyển sang tab 2, vào ribbon "Trang" → bấm "Xoay phải". Ngay sau thao tác, toàn bộ tiến trình `python.exe`/app biến mất khỏi Task Manager — **không có dialog báo lỗi, ứng dụng đóng im lặng, không kịp lưu.**

**Kết quả thực tế vs kỳ vọng:** Kỳ vọng thao tác xoay trang chỉ ảnh hưởng tab hiện tại; thực tế toàn bộ ứng dụng sập, mất luôn cả tab đang xem file gốc chưa lưu gì.

**Bằng chứng:** `app_log.txt` (faulthandler log của chính app) ghi nhận **4 lần crash** trong phiên test (~50 phút), với nội dung:
```
Windows fatal exception: code 0x8001010d
Windows fatal exception: access violation
Fatal Python error: Aborted
```

**Lưu ý về khả năng tái hiện:** Thử lại thao tác xoay trang tương tự trên **1 tab duy nhất** (không có file nặng khác đang mở song song) thì **không crash** — cho thấy nguyên nhân có tương quan với áp lực bộ nhớ/đa tab hơn là bản thân hàm xoay trang bị lỗi logic.

**Cập nhật — tái hiện lần 2 với repro đơn giản hơn, độ tin cậy cao hơn:** Mở file 711MB/336 trang (1 tab duy nhất, không đa tab), vào ribbon "Bảo mật_Xuất" → bấm **"Nén PDF"** (`app/actions/document_ops.py:633 compress_pdf`). Ngay khi bấm, tiến trình biến mất khỏi Task Manager, `app_log.txt` ghi thêm đúng 1 block crash mới (`Windows fatal exception: code 0x8001010d`, `Fatal Python error: Aborted`). Đã xác nhận file PDF nguồn **không bị hỏng** sau crash (mở lại bằng `pikepdf` vẫn đủ 336 trang) — cơ chế ghi file tạm rồi thay thế (`replace_document_with_staged`) bảo vệ tốt khỏi mất/hỏng dữ liệu khi crash giữa chừng, đây là điểm làm đúng đáng ghi nhận. Repro này **gọn hơn nhiều** so với kịch bản xoay trang đa tab ở trên (chỉ cần 1 tab + 1 thao tác nén), cho thấy nguyên nhân gốc nhiều khả năng nằm ở bước `pikepdf` ghi lại (re-save) một PDF rất lớn rồi Qt/WebEngine reload lại ngay sau đó, hơn là do riêng đa tab.

**Cập nhật — tái hiện lần 3, kịch bản rất phổ biến trong thực tế:** Đang mở file gốc 711MB (tab 1), ký số thành công 1 bản PDF khác (711MB) rồi mở file vừa ký đó qua cơ chế single-instance IPC (tương đương double-click file trong Explorer trong khi app đang chạy — xem thêm Bug #1). App crash ngay trong lúc xử lý mở tab thứ 2 cho file nặng này, thêm 1 block crash mới vào `app_log.txt`. Đây là thao tác rất đời thường: ký xong rồi mở lại file để xem — cho thấy rủi ro crash không chỉ giới hạn ở thao tác "nén"/"xoay trang" mà ở bất kỳ lúc nào có **≥2 tài liệu rất lớn cùng được xử lý/tải gần nhau về thời điểm**.

**File nghi vấn:** Đây trùng khớp với vấn đề **đã được chính đội dev ghi chú lại** trong `main.py` (dòng ~116–127): crash do CPython cyclic GC chạy trên sai thread khi hủy object Qt (QThread nền như ThumbnailLoader/OCR/rotate), gây hỏng heap Qt — dev đã tắt GC tự động (`gc.disable()`) và tự chạy `gc.collect()` định kỳ trên main thread để giảm thiểu, nhưng qua test thực tế **vẫn còn xảy ra** khi có thao tác ghi/reload/mở tài liệu rất lớn (xoay trang, nén, hoặc mở thêm 1 file nặng khi đã có file nặng khác đang mở). Đây là lỗi tầng Qt/Windows đã biết, khó fix triệt để ở tầng code ứng dụng, nhưng nên được theo dõi vì hậu quả là **mất toàn bộ phiên làm việc, có nguy cơ mất dữ liệu chưa lưu** — may mắn là file nguồn trên đĩa được bảo toàn nhờ cơ chế ghi-tạm-rồi-thay-thế.

### 3. Xuất Word (chế độ "Chuyển đổi nhanh - pdf2docx") luôn thất bại ngay lập tức, báo nhầm là "đã huỷ" thay vì báo lỗi thật

**Cách tái hiện:** Mở file PDF bất kỳ (đã test với file 711MB/336 trang) → ribbon "Bảo mật_Xuất" → "Word" → giữ nguyên lựa chọn mặc định "Chuyển đổi nhanh (Giữ Layout tĩnh - pdf2docx)" → "Xuất file" → chọn nơi lưu → Save.

**Kết quả thực tế:** Trong vòng chưa tới 0.3 giây (quá nhanh để có thể là do người dùng bấm "Hủy" trên progress dialog), ứng dụng báo lỗi **"Không thể xuất file — Da huy xuat file."** — tái hiện **3/3 lần thử**, luôn giống hệt nhau. Hai chế độ xuất Word còn lại ("Giữ nguyên Layout" và "Trích xuất cấu trúc Text") cùng "Xuất Excel" đều **hoạt động bình thường** (đã test Excel thành công trên đủ 336 trang, và test "Trích xuất cấu trúc Text" trực tiếp qua dòng lệnh cũng chạy tốt) — vấn đề chỉ nằm ở nhánh pdf2docx.

**Nguyên nhân gốc đã xác định được (chạy trực tiếp `python -m packages.document_core.export_runner docx <file> <out>` ngoài GUI để lấy lỗi thật):**
```
Thieu thu vien pdf2docx.
Cai bang lenh: pip install pdf2docx
```
Thư viện `pdf2docx` có khai báo trong `requirements.txt` (`pdf2docx==0.5.13`) và `pyproject.toml`, nhưng **không có sẵn trong `.venv` đang chạy trên máy này** (`pip show pdf2docx` → not found). Đây có thể chỉ là môi trường dev/venv trên máy test này bị thiếu cài đặt, chưa chắc ảnh hưởng bản đóng gói `dist/win` gửi cho người dùng cuối — cần người phụ trách build kiểm tra lại.

**Bug thực sự nằm ở tầng xử lý lỗi của app (bất kể nguyên nhân subprocess lỗi là gì):** `app/actions/export.py` — `_run_in_subprocess()` tạo `QProgressDialog("Đang chuẩn bị xuất file…", "Hủy", 0, 0, window)` (dòng 171) và nối `progress.canceled.connect(_cancel_proc)` (dòng 240). Khi tiến trình con thoát rất nhanh (dù do crash, thiếu thư viện, hay bất kỳ lỗi nào khác), `_finish()` (dòng 192–214) lại đi vào nhánh `state.get("cancelled")` và hiển thị thông báo cứng **"Da huy xuat file."** (dòng 211, cũng thiếu dấu tiếng Việt — nên là "Đã hủy xuất file.") thay vì lỗi thật từ `stderr_text`/`stdout_text` mà code đã thu thập sẵn ở `state["stdout"]`/`state["stderr"]`. Hậu quả: **người dùng không bao giờ biết lý do thật khiến xuất Word thất bại** (thiếu thư viện, file lỗi, hay bất cứ gì khác) — chỉ thấy dòng chữ vô nghĩa "đã huỷ" dù họ không hề bấm huỷ.

### 4. Chuyển ngôn ngữ sang English (hoặc ngôn ngữ khác) không dịch hết toàn bộ giao diện

**Cách tái hiện:** Menu "Ngôn ngữ" → chọn "English".

**Kết quả thực tế:** Đa số menu bar, tên tab ribbon, tên nút đều dịch đúng (File, Navigate, View, Tools, Page, Security, Sign, OCR, AI...). Nhưng còn sót:
- Tab ribbon cuối cùng vẫn hiển thị **"Cài đặt"** (không dịch thành "Settings").
- Nút chia sẻ vẫn hiển thị **"Nhận từ ĐT"**.
- Nhãn nhóm ribbon vẫn hiển thị **"CHIA SẺ"** (trong khi các nhóm khác cùng hàng đã dịch đúng: FILE, NAVIGATE, ZOOM, VIEW).

**Kỳ vọng:** Toàn bộ chuỗi hiển thị phải đổi theo ngôn ngữ đã chọn.

**File/hàm nghi vấn (đã xác định root cause):**
- `app/window.py:1123` — `self.ribbon.add_tab(self._t("tab.settings", "Cài đặt"), p6)`: khoá dịch `"tab.settings"` **không tồn tại** trong `app/language_manager.py` → luôn rơi về giá trị mặc định tiếng Việt `"Cài đặt"` bất kể ngôn ngữ nào đang chọn.
- `app/window.py:796` — nút `self.act_transfer_device = make("Nhận từ ĐT", ...)`: chuỗi cứng, không đi qua `self._t(...)` nên không bao giờ được dịch.
- `app/window.py:854` — `self.g_share = RibbonGroup("Chia sẻ")`: cũng là chuỗi cứng tương tự.

## MỨC NHẸ / CẦN KIỂM TRA THÊM THỦ CÔNG

### 6. Handle xoá nhanh (nút tròn đỏ "X") trên đối tượng vừa chèn — 1 lần thử không xoá được

Sau khi chèn văn bản bằng "Chèn chữ", đối tượng hiện 4 handle quanh khung chọn (di chuyển, xoay, resize, xoá — hình tròn đỏ có dấu X). Bấm vào handle đỏ này 1 lần không thấy xoá đối tượng (chỉ mất trạng thái chọn). Độ tin cậy phát hiện **thấp** — khả năng cao do thao tác click tự động lệch khỏi vùng handle nhỏ (~16px), không loại trừ hoàn toàn là bug thật. Công cụ "Xóa obj" riêng trong ribbon "Chú thích" hoạt động đúng 100% (đã xác nhận). Đề nghị người dùng tự bấm thử nhanh vào handle X để xác nhận lại.

### 7. Ghi chú phương pháp test (không phải bug ảnh hưởng người dùng)

- QSpinBox trong dialog "Xóa nhiều trang" (`app/actions/pages.py` — `_PageRangeDialog`) không phản hồi tốt với thao tác **triple-click để chọn toàn bộ nội dung** bằng công cụ automation (giá trị cũ bị nối thêm số mới thay vì thay thế, vd gõ "2" và "4" nhưng hộp xác nhận hiện "Xóa trang 4–12"). Dùng `Ctrl+A` thay cho triple-click thì hoạt động đúng. Đây là hành vi mặc định của `QAbstractSpinBox`, không phải bug code của app, nhưng gợi ý: nên tự động select-all nội dung khi field nhận focus (giống UX nhiều app khác) để giảm rủi ro người dùng gõ nhầm chồng số.
- Tương tự, một bài test đặt mật khẩu PDF bằng ô nhập tự động gõ nhanh đã bị rớt ký tự (do tốc độ gõ tự động + bàn phím tiếng Việt Telex đang bật trên máy làm biến đổi một số chuỗi gõ, không phải do app) — đã xác minh mã hoá PDF (`pikepdf.Encryption(user=pw, owner=pw+"_owner", R=6)` trong `app/actions/document_ops.py:518-522`) hoạt động đúng cơ chế; không phát hiện bug trong logic đặt mật khẩu. Ghi chú thêm: bộ gõ Telex đang bật khiến một số bước test phải chuyển sang dán clipboard thay vì gõ trực tiếp để đảm bảo đúng chuỗi ký tự.
- Xuất Excel trên file 336 trang: tiến trình con `export_runner` dùng tới **~4.7GB RAM** trong lúc xử lý — không phải bug, nhưng đáng lưu ý nếu máy người dùng có RAM hạn chế khi xuất file rất nặng.

## CHƯA TEST TRỰC TIẾP BẰNG CHUỘT (để minh bạch phạm vi báo cáo)

Báo cáo này **không phủ 100%** danh sách yêu cầu ban đầu. Dưới đây là các mục cụ thể chưa click-test trực tiếp, chia theo lý do:

**Cố ý bỏ qua (rủi ro thật, khó đảo ngược):**
- Kích hoạt/nhập License key — tránh ảnh hưởng trạng thái license thật đang active trên máy.
- Bấm "In" tới cùng ra máy in vật lý — tránh in giấy ngoài ý muốn.
- Ký PFX (không có sẵn file .pfx nào trên máy để test; đã test USB token thay thế, xem mục riêng).

**Chưa kịp test do giới hạn thời gian phiên làm việc (ưu tiên các nhóm chính trước):**
- Tệp: **Lưu**, **Lưu mới (Save As)** — chưa bấm thử trực tiếp (dù các thao tác khác như xoay/xoá trang có lưu ngầm bên trong nên cơ chế ghi file coi như đã được test gián tiếp).
- Chú thích: **Chèn ảnh**, **Vẽ tự do**, **Gạch dưới**, **Gạch ngang**, **Màu tô**, **Ghi chú (Note)** — mới thấy menu, chưa thao tác thật.
- Trang: **Ghép PDF**, **Tách PDF**, **Chèn trang trắng** — mới **review code** (`app/actions/pages.py`), chưa click-test qua GUI thật.
- Bảo mật/Xuất: **Xóa mật khẩu**, **Xuất ảnh**, **Xuất văn bản (.txt)** — chưa test.
- Chữ ký số: **Ô ký** (đặt sẵn khung chữ ký chờ ký sau), **Kiểm tra chữ ký** (Verify) — đã thử nhưng app crash trước khi xem được kết quả (xem Bug #2).
- OCR/AI: **OCR toàn bộ tài liệu** (336 trang), **Chat PDF**, **Tóm tắt tài liệu**, **Tìm kiếm theo nghĩa** — chỉ test OCR 1 trang và Dịch 1 trang (cả hai đều thành công) để tiết kiệm thời gian/chi phí AI.
- Cài đặt: **Kiểm tra key**, **Trợ giúp** (trong tab ribbon "Cài đặt") — chưa click vào.
- License menu: **Thiết bị ScanDoc**, **Chuyển tài liệu**, **Nhận tài liệu** — chưa test.

Nếu bạn muốn, tôi có thể tiếp tục test nốt các mục trên trong phiên tiếp theo.

## KHUYẾN NGHỊ ƯU TIÊN XỬ LÝ

1. **Bug #1 (tab trùng lặp)** — nên sửa trước tiên: ảnh hưởng trải nghiệm hàng ngày rõ rệt nhất, fix gọn (1 điểm kiểm tra trong `open_document()`).
2. **Bug #2 (crash, 4 lần trong phiên test)** — nghiêm trọng nhất về hậu quả (mất phiên làm việc), tái hiện qua 3 kịch bản khác nhau (xoay trang đa tab, nén PDF, mở file nặng thứ 2) đều liên quan tới **xử lý PDF rất lớn (700MB+)**. Là lỗi tầng Qt/Windows đã biết nhưng tần suất gặp trong 50 phút test (4 lần) cho thấy mức độ nghiêm trọng thực tế cao hơn ước tính ban đầu — nên ưu tiên điều tra thêm, có thể cân nhắc giới hạn/cảnh báo khi mở nhiều file rất lớn cùng lúc như một biện pháp giảm thiểu tạm thời trong lúc chưa fix gốc.
3. **Bug #3 (Xuất Word "Chuyển đổi nhanh" luôn báo huỷ thay vì báo lỗi thật)** — trước tiên kiểm tra `pdf2docx` đã có trong bản đóng gói `dist/win` hay chưa; dù nguyên nhân gốc là gì, cũng nên sửa `_finish()` trong `app/actions/export.py` để hiển thị đúng lỗi thật từ subprocess thay vì luôn báo "đã huỷ" khi `state["cancelled"]` — hiện đang che mất thông tin hữu ích để tự chẩn đoán.
4. **Bug #4 (thiếu dịch)** — mức ảnh hưởng thấp, có thể xử lý bất cứ lúc nào rảnh.
