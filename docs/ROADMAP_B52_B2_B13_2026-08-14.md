## B52 — Dùng Office/WPS có sẵn thay vì bắt buộc tải LibreOffice

### Hiện trạng thật (đã đọc code, đính chính lại cho đúng)

Yêu cầu gốc nói "đang dùng LibreOffice cho Excel" — kiểm tra lại code thì **không đúng như vậy**:

- **Xuất PDF → Excel** (`packages/document_core/converter.py::convert_pdf_to_xlsx`): thuần Python, dùng `pdfplumber` (đọc bảng) + `openpyxl` (ghi .xlsx) — **không hề gọi LibreOffice**, không có gì cần sửa ở chiều này.
- **Xuất PDF → Word** (`convert_pdf_to_docx*`): dùng `pdf2docx`/`pdfplumber`/`python-docx` — cũng không dùng LibreOffice.
- **LibreOffice chỉ dùng ở chiều NGƯỢC LẠI**: mở file Office gốc (.doc/.docx/.xls/.xlsx/.ppt...) để XEM trong app — `app/actions/document_converter.py`:
  - `get_libreoffice_bin()` (dòng 191): tìm `soffice.exe` — trước tiên ở thư mục module tự tải của app (`%AppData%/.../modules/libreoffice`), sau đó fallback `C:\Program Files\LibreOffice\program\soffice.exe`.
  - `convert_office_to_pdf()` (dòng 895): gọi `subprocess.run([soffice, "--headless", "--convert-to", "pdf", ...])` để render file Office ra PDF rồi hiển thị.
  - Nếu không tìm thấy LibreOffice: hỏi người dùng có muốn tải module ~150MB không (`download_and_extract_libreoffice`, tải từ CDN của chính 3T, không phải trang LibreOffice).

→ **B52 thực chất là: sửa `get_libreoffice_bin()`/`convert_office_to_pdf()` để ưu tiên dùng Microsoft Office hoặc WPS Office đã cài sẵn trên máy, chỉ hỏi tải LibreOffice khi máy không có cả 2 thứ đó.**

### Vì sao đây KHÔNG phải vấn đề bản quyền

Khác hẳn B2 — dùng COM Automation của Office/WPS là gọi **API công khai do chính Microsoft/Kingsoft công bố cho lập trình viên bên thứ 3** (giống hệt cách Excel add-in, macro VBA, hay hàng nghìn phần mềm kế toán/ERP khác vẫn làm). Không đụng đến mã nguồn của Office/WPS, không vi phạm gì. Vấn đề duy nhất là **kỹ thuật** (phát hiện đúng, gọi đúng, dọn dẹp đúng khi lỗi).

### Cách phát hiện Office/WPS đã cài (tham khảo cách các app lớn — Adobe Acrobat, Foxit, Kofax — làm, không chép code, chỉ theo đúng chuẩn Windows COM)

**Bước 1 — Dò registry (nhanh, không cần khởi động ứng dụng nào):**

```python
import winreg

def _com_progid_exists(prog_id: str) -> bool:
    """True nếu ProgID đã đăng ký COM trên máy (không cần khởi động app)."""
    try:
        winreg.QueryValue(winreg.HKEY_CLASSES_ROOT, f"{prog_id}\\CLSID")
        return True
    except FileNotFoundError:
        return False

def detect_office_suite() -> str | None:
    """Trả 'msoffice' | 'wps' | None theo thứ tự ưu tiên."""
    if _com_progid_exists("Excel.Application") and _com_progid_exists("Word.Application"):
        return "msoffice"
    # WPS đăng ký ProgID riêng, tương thích COM nhưng KHÔNG dùng chung
    # "Excel.Application" với Microsoft (tránh xung đột nếu máy cài cả 2).
    # Tên ProgID thật của WPS: "Ket.Application" (bảng tính), "Kwps.Application"
    # (văn bản) — CẦN xác nhận lại registry thật trên 1 máy có cài WPS trước
    # khi code chính thức (không đoán suông, xem mục "Việc cần làm" bên dưới).
    if _com_progid_exists("Ket.Application") or _com_progid_exists("Kwps.Application"):
        return "wps"
    return None
```

**Bước 2 — Convert bằng COM Automation (Word ví dụ, Excel/PowerPoint tương tự):**

```python
import pythoncom
import win32com.client

def convert_via_office_com(input_path: str, output_pdf: str, kind: str) -> bool:
    """kind: 'word' | 'excel' | 'ppt'. Trả True nếu thành công."""
    pythoncom.CoInitialize()  # BẮT BUỘC trên thread nền, xem bài học B13/TTS
    app = None
    try:
        prog_id = {"word": "Word.Application", "excel": "Excel.Application",
                   "ppt": "PowerPoint.Application"}[kind]
        app = win32com.client.Dispatch(prog_id)
        app.Visible = False
        if kind != "ppt":
            app.DisplayAlerts = False  # chặn popup "Save changes?" treo COM call
        doc = app.Documents.Open(input_path) if kind == "word" else \
              app.Workbooks.Open(input_path) if kind == "excel" else \
              app.Presentations.Open(input_path, WithWindow=False)
        # 17 = wdFormatPDF (Word), 0 = xlTypePDF (Excel), 32 = ppSaveAsPDF (PowerPoint)
        fmt = {"word": 17, "excel": 0, "ppt": 32}[kind]
        if kind == "word":
            doc.SaveAs(output_pdf, FileFormat=fmt)
        elif kind == "excel":
            doc.ExportAsFixedFormat(fmt, output_pdf)
        else:
            doc.SaveAs(output_pdf, fmt)
        doc.Close(False)
        return True
    except Exception:
        return False
    finally:
        if app is not None:
            try:
                app.Quit()
            except Exception:
                pass
        pythoncom.CoUninitialize()
```

**Bước 3 — Chuỗi fallback (đúng tinh thần bạn muốn: không bắt buộc LibreOffice):**

```
Có Microsoft Office cài sẵn?  → dùng COM Word/Excel/PowerPoint
        │ không
        ▼
Có WPS Office cài sẵn?        → dùng COM WPS (API tương thích Office)
        │ không
        ▼
Có LibreOffice cài sẵn?       → dùng soffice.exe (logic cũ, giữ nguyên)
        │ không
        ▼
Hỏi người dùng có muốn tải LibreOffice không (như hiện tại)
```

### Rủi ro kỹ thuật cần xử lý (đã có tiền lệ trong chính codebase — B13/TTS COM)

1. **Zombie process**: nếu COM automation crash giữa chừng, `WINWORD.EXE`/`EXCEL.EXE` có thể treo lại trong Task Manager dù không còn cửa sổ nào — luôn có `finally: app.Quit()`, cân nhắc thêm timeout/kill theo PID nếu `Quit()` không phản hồi sau N giây.
2. **`pythoncom.CoInitialize()`** bắt buộc nếu COM automation chạy trên thread nền (không phải main thread Qt) — xem đúng bài học đã áp dụng cho TTS SAPI trong `tts_dialog.py`.
3. **File đang mở trong Office thật của người dùng**: nếu user đang mở sẵn file đó trong Word, `Documents.Open()` có thể trả về đúng document đang mở (dùng chung instance) thay vì mở bản mới — cần test kỹ, có thể phải mở bằng bản sao tạm (`shutil.copy2` vào temp trước khi `Open()`) để tránh xung đột.
4. **Office/WPS version cũ không hỗ trợ `ExportAsFixedFormat`/`SaveAs PDF`** (chỉ có từ Office 2007+) — kiểm tra `app.Version` trước khi thử, fallback xuống LibreOffice nếu quá cũ.

## B13 — Crash Qt/GC hiếm gặp trên file rất lớn (0x8001010d / Fatal Python error: Aborted)

### Hiện trạng (đã phân tích sâu trong phiên trước — tóm tắt lại)

- **2 nghi vấn cụ thể đã loại trừ** (đã có fix từ trước, xác nhận lại 14/08): PDFium đa luồng (đã có `PDFIUM_LOCK`), COM apartment mismatch của TTS (đã có `CoInitialize`/`CoUninitialize`).
- **Còn lại đúng 1 thứ chưa fix được**: crash Qt/GC gốc, rất hiếm (93 lần/2.5 tháng theo ghi nhận cũ), chỉ mitigate bằng `gc.disable()` + timer, không có đầu mối code cụ thể để đào tiếp nếu không có repro sống mới.

### Hướng đi tiếp theo (tham khảo cách các app Qt/Chromium-based lớn xử lý crash hiếm — Chrome, Electron, VS Code — không chép code, chỉ theo đúng KIẾN TRÚC đã công khai của họ)

**1. Thu thập telemetry crash thật (ưu tiên cao nhất — không có dữ liệu thì không sửa tiếp được)**

Các app lớn (Chrome, VS Code) đều có crash reporter tự động gửi minidump về server khi crash xảy ra ở máy user thật, thay vì chỉ dựa vào QA nội bộ tái hiện được. Có thể làm bản đơn giản hơn nhiều, không cần hạ tầng lớn:
- Dùng `faulthandler.enable(file=..., all_threads=True)` (đã có sẵn theo ghi nhận cũ trong `app_log.txt`) — đảm bảo file log này **được gửi kèm khi user báo lỗi** (thêm nút "Gửi báo cáo lỗi" đính kèm `app_log.txt` + vài dòng cuối, không cần build hẳn crash-reporter server riêng).
- Ghi thêm ngữ cảnh ngay TRƯỚC lúc crash: file đang mở (kích thước), thao tác cuối cùng, RAM tại thời điểm đó — để lần crash tiếp theo có đủ dữ kiện tìm quy luật thay vì chỉ có stack trace native vô nghĩa.

**2. Kiến trúc process-isolation (giải pháp triệt để nhất, chi phí công sức lớn nhất)**

Chrome/Electron cô lập mỗi tab/renderer vào **process riêng** — 1 tab crash không kéo sập cả app. 3T Reader hiện mọi tab chạy chung 1 process Python. Nếu crash Qt/GC thật sự liên quan tới việc giữ nhiều file lớn trong cùng 1 process (nghi vấn hợp lý dựa trên pattern "đa tab file lớn" đã quan sát), tách mỗi tab thành 1 tiến trình con riêng (`QProcess` hoặc `multiprocessing`, giao tiếp qua IPC) sẽ triệt để loại bỏ khả năng 1 tab lỗi làm sập toàn app — nhưng đây là **thay đổi kiến trúc lớn**, không phải fix nhỏ, cần đánh giá kỹ trước khi bắt tay làm (ảnh hưởng hiệu năng, độ phức tạp code, thời gian phát triển).

**3. Giảm nhẹ trong lúc chưa có giải pháp triệt để**

- Giữ nguyên cảnh báo hiện tại khi mở nhiều file lớn cùng lúc.
- Cân nhắc thêm giới hạn cứng (không chỉ cảnh báo) nếu theo dõi thực tế cho thấy tần suất cao hơn ghi nhận cũ.

### Việc cần làm

- [ ] Thêm nút "Gửi báo cáo lỗi" đính kèm `app_log.txt` vào dialog crash-recovery (nếu có) hoặc splash lúc khởi động lại sau crash.
- [ ] Theo dõi thực tế qua vài tuần/tháng dùng thật, thu thập đủ 3-5 lần crash có log đầy đủ trước khi kết luận thêm.
- [ ] (Quyết định lớn, cần bạn duyệt riêng) Đánh giá chi phí/lợi ích của kiến trúc process-per-tab nếu telemetry xác nhận đúng nghi vấn "nhiều tab file lớn cùng process".

## B53 — Cập nhật vá lỗi (delta update) thay vì tải lại toàn bộ 486MB mỗi lần

### Vấn đề thật vừa trải nghiệm hôm nay

Bản 1.0.31 chỉ sửa vài trăm dòng Python (B14-B19, B13-adjacent, chữ ký update) nhưng user phải tải **nguyên 486MB** — vì PyInstaller đóng gói TOÀN BỘ runtime (Qt/PySide6 ~150MB, Tesseract OCR ~80MB, aiortc/AI SDKs, Python interpreter...) thành 1 khối, dù 99% trong số đó **không đổi** giữa các bản vá lỗi liên tiếp.

### Vì sao khó "chỉ vá đúng phần code" với cấu trúc build hiện tại

PyInstaller (chế độ mặc định, đang dùng) gom phần lớn module Python thuần vào 1 file archive nén (`PYZ`) bên trong `_internal/`, không phải để rời từng file `.py`/`.pyc` — nên **không thể** đơn giản "tải vài file .py mới rồi ghi đè" như một app Python chạy từ source. Đây là lý do B53 cần thay đổi ở tầng **kiến trúc build**, không chỉ tầng server.

### Hướng đi tham khảo (mô hình delta-update của Electron/Squirrel, Chrome, game lớn — chỉ tham khảo Ý TƯỞNG kiến trúc, không đụng code của họ)

**Nguyên tắc chung mọi hệ thống delta-update lớn đều theo:** tách phần **runtime ít đổi** (Qt, Python interpreter, Tesseract, thư viện AI) ra khỏi phần **code hay đổi** (chính app 3T Reader — `app/`, `packages/`, `assets/`), đóng gói + versioning RIÊNG cho từng phần.

**Kiến trúc đề xuất — 2 gói tách biệt:**

```
3T Reader (cài đặt)
├── runtime/          ← "Base Package" - Qt, Python, Tesseract, aiortc...
│   └── version: base-1.0 (đổi RẤT hiếm, chỉ khi nâng cấp PySide6/Qt lớn)
└── app/              ← "Code Package" - app/, packages/, assets/ của 3T Reader
    └── version: 1.0.31, 1.0.32... (đổi mỗi lần vá lỗi)
```

- **Bản vá lỗi thông thường** (như hôm nay): chỉ build lại + tải lại **Code Package** — dự kiến vài MB đến vài chục MB thay vì 486MB.
- **Nâng cấp lớn** (đổi version Qt/Python...): mới cần tải lại **Base Package**, hiếm khi xảy ra.

### Việc cần làm (thứ tự ưu tiên — làm dần, không cần xong hết 1 lần)

- [ ] **Bước 1 (rẻ nhất, làm trước):** đo thử tách `3T_Reader.spec` (PyInstaller) thành 2 lần build riêng — 1 lần build "base" (mọi thứ trừ `app/`/`packages/`/`assets/`), 1 lần build "app code" — xác nhận app vẫn chạy đúng khi 2 phần ghép lại từ 2 thư mục khác nhau trước khi đầu tư tiếp.
- [ ] **Bước 2:** sửa `packages/updater/update_client.py` + backend `/api/v1/update/check` để trả thêm field `code_package_url`/`code_package_sha256` riêng (giữ nguyên `download_url` full installer làm fallback cho user cài mới/base đổi).
- [ ] **Bước 3:** viết logic phía app: khi có bản vá và `base_version` hiện tại khớp `base_version` server yêu cầu → chỉ tải Code Package, giải nén đè lên đúng thư mục `app`/`packages`/`assets` trong bản cài hiện tại, không đụng `runtime/`.
- [ ] **Bước 4:** cơ chế an toàn bắt buộc — verify chữ ký + SHA-256 cho CẢ Code Package riêng (đúng bài học B53 kế thừa từ lỗi chữ ký hôm nay: đừng lặp lại sai lầm import xuyên package cho phần verify mới này), và có đường lùi (nếu vá lỗi bằng Code Package thất bại giữa chừng, tự động fallback tải full installer thay vì để app ở trạng thái half-patched hỏng).
- [ ] **Bước 5:** test kỹ: vá liên tiếp nhiều lần (1.0.31 → 1.0.32 → 1.0.33 chỉ bằng Code Package) không được làm rơi rớt file, so sánh app sau nhiều lần vá delta với app cài mới hoàn toàn từ installer full — phải giống hệt nhau.

**Lưu ý quan trọng:** đây là thay đổi kiến trúc build + updater, rủi ro cao hơn 1 bug fix thường (nếu làm sai, user có thể bị "half-patched" — code mới ghép runtime cũ không tương thích) — nên làm ở nhánh riêng, test kỹ trước khi đưa vào bản chính thức, KHÔNG vội đẩy thẳng lên production như các fix hôm nay.
